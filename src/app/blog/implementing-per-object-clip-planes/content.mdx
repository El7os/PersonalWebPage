## Introduction
In modern real-time rendering, specialized visual effects, gameplay mechanics, and visualization tools often require geometry to be dynamically clipped.
While Unreal Engine 5 provides robust support for global clip planes—typically utilized for planar water reflections—it 
lacks out-of-the-box support for isolating this behavior on a per-object basis.

When global clip planes are enabled, Unreal Engine uses one of the hardware's clip-distance slots to discard vertices before rasterization.
The plane's position and orientation are defined per camera, which is ideal for reflections; however, this applies uniformly 
to every object that the camera draws. While different cameras can carry different global planes, every primitive within a single 
view shares the same cutting boundary. This global scope is the exact bottleneck our implementation addresses.

The Per-Object Clip Plane implementation described here is positioned as an extension to existing global clip plane other than a discrete implementation.
While the framework presented in this document serves as an extention, it is possible to construct a fully standalone implementation as well.

Modern graphics APIs typically expose six to eight hardware clip-distance slots simultaneously. Unreal Engine utilizes the first clip distance value to 
clip vertices using global clip plane. This implementation occupies a different slot than the engine's global clip plane so that both can coexist: water reflections 
retain their camera-driven plane, while individual objects can carry their own.

Implementing per-object clip planes allows developers to slice, hollow out, or selectively cull geometry on specific primitives without 
affecting adjacent elements in the scene. This capability is crucial for applications ranging from architectural visualizations and medical 
imaging to sci-fi cross-section effects.

The goal is to extend Unreal Engine's existing global clip-plane architecture by defining the plane used to derive clip distances 
on a per-object basis, enabling each primitive to expose its own independent cutting boundary. This utilizes the same underlying 
hardware feature and identical dot-product mathematics, but introduces a separate control lane that artists and gameplay systems 
can drive independently.

Before diving into the engine souce code to integrate this extension, a close examination of how graphics hardwares nativelly processes clipping boundaries under the hood is required.

## Clip Planes and Where to Find Them

In computer graphics, rendering hardware relies on a dedicated set of distances to determine whether a vertex should be preserved or clipped.
Rather than executing software-side culling algorithms, modern graphics APIs (such as DirectX, Vulkan, and OpenGL) natively 
expose specialized hardware registers allocated for these clip distances, typically supporting a minimum of six to eight simultaneously.

During the vertex processing stage of the rendering pipeline, the hardware evaluates these distance values.
If a vertex yields a negative clip distance, the hardware rasterizer clips the primitive along this boundary, cleanly discarding non-visible
fragments before they ever reach the pixel shader. Essentially, the hardware monitors each active clip distance slot and discards the vertex
if even a single distance value falls below zero.

Generally, developers use a plane equation to derive this clip distance value. An arbitrary plane is defined, and the clip distance
is calculated as the signed distance from the vertex to that plane. If the vertex lies in the positive half-space—the side the plane
normal points toward—the distance value is positive and the geometry is preserved. Conversely, if it lies on the opposite side, the distance
value becomes negative, triggering the hardware to clip the vertex.

<MathBlock
  latex="Clip Distance = SignedDistanceToPlane(Q)"
  caption="Setting the clip distnace to the distance of point Q to a plane"
  size="large"
/>

Because using a plane equation to derive these values is the industry-standard approach, this hardware feature is universally referred to as "clip planes."

Out of the box, Unreal Engine supports a global clip plane feature. When enabled, the engine evaluates every vertex against a single 
plane defined on a per-camera basis to derive its clip distance. The term "global" reflects the fact that this
boundary applies uniformly to every object rendered by that specific camera—though different cameras can maintain entirely distinct
global clip planes.

The objective of this implementation is to extend this capability to a per-object basis. By utilizing the exact same
underlying hardware mechanics, but define the clip plane dynamically per-primitive so that individual objects can maintain
their own unique cutting boundaries.Because modern graphics APIs support multiple concurrent clip distances, assigning the Per-Object Clip Plane to a dedicated hardware slot ensures seamless coexistence with the native global clip plane.

Before diving into the implementation it is important to understand how the clip planes are 
represented and the signed distance is calculated.

### Compact Plane Representation

Mathematically, an infinite plane is defined by the following equation:

<MathBlock
  latex="\vec{N} \cdot (\vec{P} - \vec{P}_0) = 0"
  caption="Plane Equation"
  size="large"
/>

Where $\vec{N}$ is the surface normal vector of the plane and $\vec{P}_0$ is an arbitrary point lying on that plane.


<p align="center">
  <img src="/blog/implementing-per-object-clip-planes/Image_Plane.svg" alt="Plane"></img>
</p>


Evaluating this formulation indicates taht representing a 3D plane in world space requires two <CodeInline>FVector3f</CodeInline>s; 
one for the plane normal ($\vec{N}$) and another for the surface point ($\vec{P}$).


<CodeBlock
  code={`

struct FMyPlane
{
    FVector3f PlaneNormal;
    FVector3f SurfacePoint;
};
`}
  filename=""
/>

However, it is totally possible to reduce the memory footprint of a plane by representing it in much more compact form. This special form requires
the surface point $\vec{P}_0$ to be selected as the following.

<MathBlock
  latex="\vec{P}_0 = D_p * \vec{N}"
  caption=""
  size="large"
/>

Geometrically, this approach defines $\vec{P_0}$ as the intersection point in between plane normal $\vec{N}$ and the plane surface.

<p align="center">
  <img src="/blog/implementing-per-object-clip-planes/Image_Plane_WithWorldOrigin.svg" alt="PlaneWithWorldOrigin"></img>
</p>

Under this conditions, a plane can be represented by the plane normal $\vec{N}$ and the plane distance $D_p$ to represent a plane which, can fit into an
<CodeInline>FVector4f</CodeInline> whose first three elements $(X, Y, Z)$ storing the plane normal and storing $D_p$ as the last element ($W$).

 <CodeBlock
  code={`

struct FMyCompactPlane
{
    FVector4f Plane;
};
`}
  filename=""
/>

This compact representation reduces the memory footprint of each plane by two floating-point values—a 33% reduction in memory overhead per instance. Furthermore, storing the plane in a single 4D vector enables GPU-friendly dot-product instructions during distance evaluation.

### Evaluating Point-Plane Distance (The Magic Dot Product)

When clipping vertices along a plane, calculating the signed distance from a point to that
plane is an unavoidable necessity. While there are multiple ways to interpret this mathematically,
one specific geometric interpretation proves incredibly elegant for shader execution.

To establish this calculation within the rendering pipeline, the core variables and objectives are defined as follows:

* $\vec{Q}$: The point of interest, representing the vertex position in world space.
* $D_Q$: The signed distance of the query point $\vec{Q}$ from the clipping plane,
  which is going to be referred to as the clip distance moving forward. The primary goal is to solve for this value.
* $D_P$: The scalar distance satisfying the equation $\vec{P}_0 = D_P \cdot \vec{N}$. In other words, it represents the signed perpendicular distance of the plane from the world origin along the normal vector.

The shortest distance from an arbitrary point to a plane is always measured along a path perpendicular to that plane. Because the plane normal $\vec{N}$ is by definition perpendicular
to the surface, $D_Q$ can be computed by projecting the query point $\vec{Q}$ onto the plane
normal. The difference between this projected distance and the plane's own distance from 
the origin ($D_P$) yields the exact signed distance $D_Q$.


The geometric interpretation is illustrated below:


<p align="center">
  <img src="/blog/implementing-per-object-clip-planes/Image_Plane_Distance.svg" alt="Plane"></img>
</p>

Therefore, the relationship can be expressed as:

<MathBlock
  latex="D_Q = \vec{Q} \cdot \vec{N} - D_P"
  caption=""
  size="large"
/>

By expanding and slightly rearranging this equation, a magnificent algebraic shorthand reveals itself:

<MathBlock
  latex="\begin{align*}
         D_Q &= \vec{Q} \cdot \vec{N} - D_P \\
         D_Q &= Q_X * N_X + Q_Y * N_Y + Q_Z * N_Z - D_P * 1 \\
         D_Q &= <N_X, N_Y, N_Z, -D_P> \cdot <Q_X, Q_Y, Q_Z, 1> 
         \end{align*}"
  caption=""
  size="large"
/>


Notice that the left-hand operand is almost identical to previously discussed 4D 
vector representation of the plane, with the minor exception that the distance 
term $D_P$ is negated. The right-hand operand is simply the query point represented 
as a homogeneous 4D coordinate, obtained by appending $1$ as its $W$ component. 
Evaluating the dot product of these two 4D vectors directly yields the signed clip 
distance of $\vec{Q}$.

This means that if the $D_p$ term is negated while representing the clip plane, then calculating 
the distance of point $\vec{Q}$ from the clip plane is as trivial as evaluating the dot product of the plane and the point 
represented as a homogeneous 4D coordinate.

## Implementation Blueprint
Bridging the gap between gameplay logic and raw hardware clipping requires establishing a unified, sequential data pipeline that spans all the way from a primitive component down to the HLSL vertex shaders. A top-down approach is used to trace the data's journey sequentially through Unreal Engine's architectural layers. Along this path, the primary objective is to safely ferry parameters across the asynchronous Game Thread and Render Thread boundary without inviting thread race conditions or memory corruption, before neatly packing them across the CPU-to-GPU memory interface.

## Extenting Primitive Component

Needless to say primitive component are one of the core objects of the Unreal Engine's game world. It defines a base class for all components 
that possesses a visual representation or physical volume in the game world. Therefore, <CodeInline>UPrimitiveComponent</CodeInline> class is selected to be the base class to insert the Per-Object Clip plane implementation to it.

Primitive components plays the role of the starting point in this implementation. It defines the necessary variables to define a clip plane, which is used to derive 
the clipping boundaries for the object.

Per-Object Clip Plane feature is defined in per-object basis and it is not required to have it enabled on every primitive
component in the scene, it is required to define a boolean flag parameter, in addition to the plane itself, indicating whether the clip plane is enabled for that primitive or not.

With the current setup, the variables to defines are the following

* A boolean flag indicating whether the component has an active per-object clip plane.

* A <CodeInline>FVector3f</CodeInline> representing the surface normal vector of the clip plane in world space.

* A floating-point value representing the signed perpendicular distance of the clip plane from the world origin.

## Scene Proxies

In Unreal Engine, gameplay logic is executed on the Game Thread (GT), while rendering operations—such as updating vertex buffers and managing textures—occur asynchronously on the Render Thread (RT).
To safely handle this multi-threaded split, the engine creates mirrored representation objects on the render thread for components living on the game thread.
These objects are known as Scene Proxies. 

Different game object types can be represented by distinct proxy classes. For instance, an <CodeInline>UPrimitiveComponent</CodeInline> is represented by a 
<CodeInline>FPrimitiveSceneProxy</CodeInline>, whereas an <CodeInline>USkyLightComponent</CodeInline> is 
represented by a proxy of type <CodeInline>FSkyLightSceneProxy</CodeInline>. Each proxy stores only the rendering-specific data required by the GPU and has no direct access to the source component's state or logic.

<Notification>
The same pattern is preserved with game thread - physics context, but with physics proxies
instead.
</Notification>

Although data can flow in either direction, information typically moves from the source component to the proxy.
The core challange of having a mirror object to live on another thread is keeping them synchornized as the game state changes.
Before diving down how synchronization is performed it is required to extent the <CodeInline>FPrimitiveSceneProxy</CodeInline> so that it can have the variables to be synchronized in the first place.

<CodeBlock
  code={`
//Header file
struct FPrimitiveSceneProxy
{
  //...
  /** Enable per object clip plane on this object, it is not used if r.Allow.GlobalClipPlane is not enabled.*/
  uint8 bPerObjectClipPlaneEnabled : 1;
 
        
  /**
  * Per object clip plane defined in global space
  * (x,y,z) represents the plane normal in world space (normalized)
  * w represents the distance of the plane from the world origin. It's negated.
  */
  FVector4 PerObjectClipPlane;
 
}

`}
  filename=""
/>

Engine utilizes an event-driven system to provide component-proxy synchronization. Because thousands of component-proxy pairs may exist concurrently, polling or updating every proxy per frame would severely degrade frame rates. The system has three distinct mechanisms for proxy synchronization:

1. Initialization on Creation: When a rendering-related component registers with the scene, its corresponding scene proxy is instantiated. During construction, 
   the proxy reads all relevant parameters from the source component, beginning its lifecycle in a synchronized state.
2. In-Place Dynamic Updates: An existing scene proxy can be updated dynamically to reflect runtime changes made on its source component.
   For example, modifying a component's Custom Primitive Data (CPD) floats triggers a targeted update that pushes only the modified values to the existing proxy.
3. Recreation (Teardown and Rebuild): If an existing proxy cannot be modified in place to reflect a specific change, it is destroyed and completely recreated,
   forcing full synchronization during construction. A prime example of this is toggling a light's shadow-casting property; 
   because of cached lighting interactions with the scene, updating the active proxy dynamically is not supported. Instead, the engine tears down and rebuilds the proxy.
   This recreation method is also the standard mechanism for applying structural changes made at edit time via the Details Panel, even if an in-place update pathway exists.
   It is required to call <CodeInline>MarkRenderStateDirty</CodeInline> to tell the engine that current state of the proxy does no longer represents the contemporary rendering 
   state of the source component, hence to recreate the existing proxy.

provide the ability to store a description to create a scene proxy later with or without the source component being presented at the time.

### Recreation (Teardown and Rebuild)

It is more convenient to cover teardown path since it is closely releated to synchronization through recreation of the proxy. This path generally taken by the engine when 
it is not possible to update the state of the proxy to synchonize it with the source component. The reason can vary but the common part is that the engine cannot decide that by itself.
It has to be notified about the situation. This is when <CodeInline>MarkRenderStateDirty</CodeInline> function becomes handy. 

It is enough to call <CodeInline>MarkRenderStateDirty</CodeInline> when we want to force teardown. Since our implementation has no properties that can only be updated during creation therefore 
we are only required to teadown existing scene proxyies when a per-object clip plane property gets changed through details panel. 


<CodeInline>UPrimitiveComponent::PostEditChangeProperty(FPropertyChangedEvent& )</CodeInline> function gets called by the editor when a property gets changed via details panel
while in the editor. It is possible to detect changes on per-object clip plane parameters in that function. In fact the editor does the same. Inspect the following

### In-Place Dynamic Updates

Even though recreation option always ensures the synchronization, it is generally not preferred to synchronise a primitive proxy with its source component during runtime. Creating 
a scene proxy is a non-trivial operation and generally has some performance effects. For example when a light proxy gets created the engine calculates and caches its interaction with the game scene 
which requires some degree of random memory access. 

To evade from that cost the general pattern is to provide functions to update scene proxies in place. External code and the source component can use those functions to synchronize the component 
and the proxy. 
But there is a danger along the way, race conditions. 

<Notification>
A race condition occurs when two or more processes or threads access and modify 
the same data at the same time, and the final result depends on the order in which 
they run. Without proper coordination, this can lead to incorrect or unpredictable results.
</Notification>

Since scene proxies lives in the render thread, any mutation from other threads must be managed carefully to prevent any race conditions.
It is a widely used pattern to define different versions of the same function for each relevant thread, the do the same thing safely at the end with the thread information
is given implicitly.That is what we are going to do here as well. We are going to define <CodeInline>SetPerObjectClipPlaneEnabled</CodeInline>
and <CodeInline>SetPerObjectClipPlane</CodeInline> functions to set the <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> and <CodeInline>PerObjectClipPlane</CodeInline>
respectfully for the render and game thread. These functions are going to be named as

* <CodeInline>SetPerObjectClipPlaneEnabled_GameThread</CodeInline> : Sets the <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> variable, to be called within the game thread.
* <CodeInline>SetPerObjectClipPlaneEnabled_RenderThread</CodeInline> : Sets the <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> variable, to be called within the render thread.
* <CodeInline>SetPerObjectClipPlane_GameThread</CodeInline> : Sets the <CodeInline>PerObjectClipPlane</CodeInline> variable, to be called within the game thread.
* <CodeInline>SetPerObjectClipPlane_RenderThread</CodeInline> : Sets the <CodeInline>PerObjectClipPlane</CodeInline> variable, to be called within the render thread.

First let us define the render thread versions of the functions since they are simpler.

On the other hand game thread versions of the functions cannot perform a similar mutation. What we are going to do is to queue a render command which changes the value of the variables to be executed
within the render thread. <CodeInline>ENQUEUE_RENDER_COMMAND</CodeInline> macro becomes handy here since it is designed to provide a way for developrs to enqueue render commands within threads other than
render. These comamnds are then gets executed in the same order as they are queued at the start (not exactly, startish to be fair) of the render thread.

## Setting Up The Uniform Buffers

At this point primitive scene proxies are fully synchroinized to the per-object clip plane state of their source components.
However, this information is not yet usefull; it resides entirely on the CPU and has not been sent out to the GPU, which is the next step of the implementation.

Sending data to the GPU fundamentally different from updating a variable on an Actor or pushing data to the user interface for display.
Having two disctinct physical memory components hence two different memory spaces makes it far more complex and error prone 

While graphics APIs offer several ways to transfer data on the GPU, only one is relevant to this use case: uniform buffers.

### What Is An Uniform Buffer

Uniform buffers are dedicated GPU memory regions that store data shared across a shader execution. They can be accessed by shader threads and generally contain information about the shader state, the object being rendered or the state of the computation. 

While shader cannot mutate a uniform buffer during execution, the CPU can update its contents prior to a draw call. It is usefull handy when applying the same shader to different object or different contexts. For instance when unreal compiles the shader out of a material it does not change or recompile it for every object insance that uses the same material. It only updates the uniform buffers dedicated to that shader with the information of the object being drawn.

Because per-obeject clip plane parameters are a part of the objects render state and does not change depending on the vertex being computed or the pixel being drawn they are ideal candidates to put into an uniform buffer. 

### The Implict Memory Contract

Since uniform buffers are basically raw memory regions they can contain any type of information. This may not seem like an issue at first glance but since it can contain any information knowing the memory layout of the buffer becomes a problem. It is not possible to tell if an eight bits long uniform contains eight different boolean flags or an unsigned integer size of a byte by just looking at the raw memory in the buffer. Knowing the memory layout of the information beforehand is crucial, otherwise it would be playing lottery with the raw memory to get a meaningfull information out of it.

An uniform buffer has to be read by following the rules of the memory layout just as the same layout as it is sent from the CPU. Even shifting a single bit would corrupt the whole buffer. Therefore it is safe to say that it requires a hidden contract in between CPU and GPU.

### Data Transmission To Uniform Buffers

Unreal begins the process by scanning through the render scene to collect the rendering state of all relevant objects. 
These states along with many other scene data then gets serialized into a stream of <CodeInline>FVector4f</CodeInline> elements.
In this context, these elements serve as the fundamental raw memory units for Unreal Engine.This serialized stream is then pushed accorss CPU-GPU boundary. Upon receiving the data the GPU deserializes it to reconstruct the scene state on the GPU side.

Because this process is a performance heavy task, Unreal does not regather and transmit new render states each frame, but rahter updates only the render states of the objects that are either newly created or updated. Consequently, if a static mesh actor remains unchanged in the scene, the rendering state representing its primitive scene proxy is not re-sent to the GPU.

The goal of this implementation is not to rewrite this infrasturcture, but change it enough so that primitive proxies transmit their per-object clip plane

#### Per-Object Clip Plane Enabled Flag Parameter

Adding a boolean flag parameter is a little bit tricky specially when it is compared to the clip plane parameter. 
The difference arises due to boolean variables' rare property of only requiring one bit but occupying 8 bits on the memory instead. 
This is because the minimum addressable memory unit in our computers is one byte (8 bits in most cases) not one bit. 

This is generally omitted while writing code since 7 bits are not that much memory. But when it comes to sending data to 
in between peripherals every bit counts. Sending more data than needed can tank the performance. To mostly avoid this issue Unreal tightly packs every data
as much as possible, booleans included. Instead of using a byte of memory to send a boolean flag unreal allocates an 32 bit floating point memory and uses each bit to
store the information of a different boolean flag, hence uses one bit of memory to send a boolean variable.

## Step 4: The Finishing Touch—Shader Modifications (HLSL Stage)

At this point the clip plane lives in GPU memory, patiently waiting to do its job. The CPU side of the house is in order; what remains is teaching the vertex shader to read that packed data and write a clip distance the rasterizer understands. This is where our earlier dot-product math pays off—we already know exactly what value to emit.

### Intercepting Primitive Data in SceneData.ush

Unreal centralizes per-primitive fetches in <CodeInline>SceneData.ush</CodeInline>. Any shader that calls <CodeInline>GetPrimitiveData</CodeInline> expects a stable layout: the flag bit we claimed in <CodeInline>SceneDefinitions.h</CodeInline> and the float4 at stride index 34 must be mirrored here so HLSL sees the same contract the C++ <CodeInline>Setup()</CodeInline> function wrote. We extend the struct and accessor helpers so materials and vertex factories can query <CodeInline>PerObjectClipPlane</CodeInline> without bespoke uniform slots.

# Updating The Shaders
Everything up to this point served a single purpose: sending our per-object clip plane data to the GPU. Now, it's time to update the shaders to perform the actual vertex culling.

We designed our per-object clip plane as an extension of Unreal's existing global clip plane. That architectural choice pays off here: instead of deriving a custom code path
(though you are free to do so in your own implementation), we can simply inject our logic directly into any existing code path related to the global clip plane. 

But before it is required so have a short information about how clip distances and other system variables are handled by the engine.

System variables are special variables defined by graphics APIs that can alter different aspects of the execution. Each graphics API defines a different set of system varialbes which makes it
API dependent. To solve the dependency Unreal Engine Puts an abstraction layer on top of that by defining its own variables that maps to those system variables. To indicate that spesific variables
Unreal puts <CodeInline>SV_</CodeInline> prefix to their names.

As you may already guessed clip distances are one of those variables and different graphics APIs defines a different number of clip distance variables. Luckly every API defines enough number of clip distances
for our implementation. Unreal utilizes the first clip distance variable <CodeInline>SV_ClipDistance</CodeInline> for global clip planes. <CodeInline>SV_ClipDistance</CodeInline> value is modified by several 
vertex shaders, but the code below displays the common pattern shared by all the shaders.

The only thing the holds us back from actually extending every shader that manipulates <CodeInline>SV_ClipDistance</CodeInline> and update their function body like above 
is the absense of the information coveyed by these three variables <CodeInline>bPerObjectClipPlaneEnabled</CodeInline>, <CodeInline>ClipPlane</CodeInline>, and <CodeInline>VertexPos</CodeInline>.

<CodeInline>VertexPos</CodeInline> is a good starting point since it is the easiest one any requires so little effort. Let us tackle that first before getting to the real challange. 
Initially one might think to use the <CodeInline>WorldPos</CodeInline> as the <CodeInline>VertexPos</CodeInline> as it is being used in global clip plane calculation.
Even though it is partially correct it is not the right answer. <CodeInline>WorldPos</CodeInline> variable contains the position of the vertex relative to the camera position in the world.
It makes sense since global clip plane is actually computed relatively to the camera position. When global clip plane is far way 1000 units it doesn't indicate a world position it
indicates the object whose distance from the camera is greater than 1000 untits are clipped. 
We need to convert it into actual world space position of the vertex before using it in our calculation.

Calculation is trivial, it is only required to add the camera world position to the <CodeInline>WorldPosition</CodeInline>.
