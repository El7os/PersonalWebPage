## Introduction
In modern real-time rendering, specialized visual effects, gameplay mechanics, and visualization tools often require geometry to be dynamically clipped.
While Unreal Engine 5 supports global clip planes—typically utilized for planar reflections, such as water surfaces or mirrors—it
lacks out-of-the-box support for isolating this behavior on a per-object basis.

When the global clip plane is enabled, Unreal Engine employs one of the hardware's clip-distance slots to discard geometry before rasterization.
The plane's position and orientation are defined per view, which is ideal for reflections; however, the plane applies uniformly
to every object rendered in that view. Different views can carry different planes, but every primitive within a single
view shares the same cutting boundary. This global scope is the exact limitation our implementation addresses.

Per-object clip planes allow developers to slice geometry on specific primitives without
affecting adjacent elements in the scene. This is useful in applications ranging from architectural visualization and medical
imaging to sci-fi cross-section effects.

Rather than a standalone feature, the per-object clip plane described here is an extension of the existing global clip plane.
It relies on the same hardware feature and the same dot-product math, but adds a separate control path that artists and gameplay systems
can drive independently. A fully standalone implementation is also possible, but it is outside the scope of this article.

Before diving into the engine source code, let us take a close look at how graphics hardware handles clipping under the hood.

## Clip Planes and Where to Find Them

In computer graphics, rendering hardware relies on a dedicated set of distances to determine whether geometry should be preserved or clipped.
Rather than leaving this to software-side clipping algorithms, modern graphics APIs (such as DirectX, Vulkan, and OpenGL) natively
expose specialized hardware slots for these clip distances, typically supporting at least eight simultaneously.

During the vertex processing stage, the vertex shader writes a distance value into each active slot.
If a vertex yields a negative clip distance, the hardware rasterizer clips the primitive along the boundary where the interpolated distance crosses zero, cleanly discarding non-visible
fragments before they ever reach the pixel shader. In short, the hardware checks every active clip distance slot and discards any region of a triangle
where even a single distance falls below zero.

Generally, developers use a plane equation to derive this clip distance value. An arbitrary plane is defined, and the clip distance
is calculated as the signed distance from the vertex to that plane. If the vertex lies in the positive half-space—the side the plane
normal points toward—the distance is positive and the geometry is preserved. If it lies on the opposite side, the distance
becomes negative, causing the hardware to clip the geometry.

<MathBlock
  latex="Clip Distance = SignedDistanceToPlane(Q)"
  caption="Setting the clip distance to the signed distance from point Q to a plane"
  size="large"
/>

The name comes from older graphics APIs, where developers handed plane equations directly to the hardware. Modern APIs generalized this to
arbitrary distances, but since planes remain the most common use, the feature is still commonly referred to as "clip planes."

Unreal Engine's global clip plane is built on exactly this mechanism. When enabled, the engine evaluates every vertex in the passes that support it against a single
plane defined per view, and writes the result into the first clip distance slot.

Our implementation follows the same approach, but defines the plane per primitive instead of per view. Since modern graphics APIs support
multiple concurrent clip distances, the per-object clip plane gets a dedicated slot of its own, allowing it to coexist with the global clip plane:
planar reflections keep their view-driven plane, while individual objects carry their own.

First, though, we need to understand how clip planes are represented and how the signed distance is calculated.

### Compact Plane Representation

Mathematically, an infinite plane is defined by the following equation:

<MathBlock
  latex="\vec{N} \cdot (\vec{P} - \vec{P}_0) = 0"
  caption="Plane Equation"
  size="large"
/>

Where $\vec{N}$ is the surface normal vector of the plane and $\vec{P}_0$ is an arbitrary point lying on that plane.


<p align="center">
  <Img src="/blog/implementing-per-object-clip-planes/Image_Plane.svg" alt="Plane" />
</p>


Looking at this equation, we can see that representing a 3D plane in world space requires two <CodeInline>FVector3f</CodeInline>s:
one for the plane normal ($\vec{N}$) and another for the surface point ($\vec{P}_0$).


<CodeBlock
  code={`
struct FMyPlane
{
    FVector3f PlaneNormal;
    FVector3f SurfacePoint;
};
`}
  filename=""
/>

However, it is entirely possible to reduce the memory footprint of a plane by representing it in a much more compact form. This special form requires
the plane normal $\vec{N}$ to be unit length, and the surface point $\vec{P}_0$ to be selected as follows:

<MathBlock
  latex="\vec{P}_0 = D_P \cdot \vec{N}"
  caption=""
  size="large"
/>

Geometrically, this approach defines $\vec{P}_0$ as the intersection point between the plane surface and the line that passes through the world origin along the plane normal $\vec{N}$.

<p align="center">
  <Img src="/blog/implementing-per-object-clip-planes/Image_Plane_WithWorldOrigin.svg" alt="PlaneWithWorldOrigin" />
</p>

Under these conditions, a plane can be represented by the plane normal $\vec{N}$ and the plane distance $D_P$ alone, which fits into one
<CodeInline>FVector4f</CodeInline>: the first three elements $(X, Y, Z)$ store the plane normal and the last element ($W$) stores $D_P$.

<CodeBlock
  code={`
struct FMyCompactPlane
{
    FVector4f Plane; // XYZ: plane normal, W: plane distance
};
`}
  filename=""
/>

<Notification>
In fact, Unreal's own <CodeInline>FPlane</CodeInline> uses exactly this representation: it stores the plane normal in $X$, $Y$, $Z$ and $D_P$ in $W$,
and <CodeInline>FPlane::PlaneDot</CodeInline> returns $\vec{N} \cdot \vec{P} - W$.
</Notification>

This compact representation reduces the memory footprint of each plane by two floating-point values—a 33% reduction in memory per plane. Furthermore, storing the plane in a 4D vector allows the distance to be evaluated with a single GPU-friendly dot product, as the next section shows.

### Evaluating Point-Plane Distance (The Magic Dot Product)

When clipping vertices along a plane, calculating the signed distance from a point to that
plane is unavoidable. While there are multiple ways to approach this mathematically,
one specific geometric interpretation proves incredibly elegant for shader execution.

Let us first define the core variables:

* $\vec{Q}$: The point of interest, representing the vertex position in world space.
* $D_Q$: The signed distance of the query point $\vec{Q}$ from the clipping plane,
  which we will refer to as the clip distance from here on. The primary goal is to solve for this value.
* $D_P$: The scalar distance satisfying the equation $\vec{P}_0 = D_P \cdot \vec{N}$. In other words, it represents the signed perpendicular distance of the plane from the world origin along the normal vector.

The shortest distance from an arbitrary point to a plane is always measured along a path perpendicular to that plane. Because the plane normal $\vec{N}$ is by definition perpendicular
to the surface, $D_Q$ can be computed by projecting the query point $\vec{Q}$ onto the plane
normal. The difference between this projected distance and the plane's own distance from
the origin ($D_P$) yields the exact signed distance $D_Q$.

The illustration below shows this geometrically:

<p align="center">
  <Img src="/blog/implementing-per-object-clip-planes/Image_Plane_Distance.svg" alt="Plane Distance" />
</p>

Therefore, the relationship can be expressed as:

<MathBlock
  latex="D_Q = \vec{Q} \cdot \vec{N} - D_P"
  caption=""
  size="large"
/>

By expanding and slightly rearranging this equation, a magnificent algebraic shorthand reveals itself:

<MathBlock
  latex="\begin{align*}
         D_Q &= \vec{Q} \cdot \vec{N} - D_P \\
         D_Q &= Q_X N_X + Q_Y N_Y + Q_Z N_Z - D_P \cdot 1 \\
         D_Q &= \langle N_X, N_Y, N_Z, -D_P \rangle \cdot \langle Q_X, Q_Y, Q_Z, 1 \rangle
         \end{align*}"
  caption=""
  size="large"
/>


Notice that the left-hand operand is almost identical to the previously discussed 4D
vector representation of the plane, with the minor exception that the distance
term $D_P$ is negated. The right-hand operand is simply the query point represented
as a homogeneous 4D coordinate, obtained by appending $1$ as its $W$ component.
Evaluating the dot product of these two 4D vectors directly yields the signed clip
distance of $\vec{Q}$.

In other words, storing the $D_P$ term negated reduces the whole calculation to one <CodeInline>dot</CodeInline> call in HLSL,
with no extra subtraction and no special cases. This is exactly the convention used throughout the rest of this implementation: whenever the plane is packed
into a 4D vector, its $W$ component holds $-D_P$.

## Implementation Blueprint
Bridging the gap between gameplay logic and raw hardware clipping requires establishing a unified, sequential data pipeline that spans all the way from a primitive component down to the HLSL vertex shaders.
A top-down approach is used to trace the data's journey through Unreal Engine's architectural layers. Along this path, the primary objective is to safely ferry parameters across the
boundary between the asynchronously running game thread and render thread without inviting race conditions or memory corruption, before neatly packing them for the trip from the CPU to the GPU.


<p align="center">
  <Img src="/blog/implementing-per-object-clip-planes/Image_ToDo.svg" alt="Implementation Blueprint" />
</p>

The journey is split into the following stages, each of which gets its own section below:

1. **Extending the primitive component** (game thread): defining the clip plane properties, along with their getters and setters.
2. **Scene proxies** (game thread → render thread): carrying the information to the render-side mirror of the component, and keeping the two in sync
   through creation, recreation and in-place updates.
3. **Sending the data to the GPU** (render thread → GPU): requesting uniform buffer updates, adding the data to the primitive's uniform shader parameters,
   and serializing them into the stream the GPU receives.
4. **GPU deserialization** (GPU): unpacking the data on the GPU, so that the CPU and the GPU agree on where it lives.
5. **Clipping vertices** (GPU): writing the per-object clip distance in the vertex shaders, and making every vertex factory provide the data those shaders need.


## Extending the Primitive Component

Primitive components are among the core objects of Unreal Engine's game world. <CodeInline>UPrimitiveComponent</CodeInline> is the base class for all components
that possess a visual representation or physical volume in the game world, which makes it the natural host for the per-object clip plane.

Primitive components serve as the starting point of our data pipeline. They define the variables that describe the clip plane, which is later used to clip
the object.

Since not every primitive in the scene needs a clip plane, we also need a boolean flag indicating whether the feature is enabled for that primitive,
in addition to the plane itself.

In summary, the variables to define are the following:

* A boolean flag indicating whether the component has an active per-object clip plane.

* An <CodeInline>FVector</CodeInline> representing the surface normal vector of the clip plane in world space.

* A floating-point value representing the signed perpendicular distance of the clip plane from the world origin.

Notice that on the component side the plane is stored in its human-friendly form (a normal and a distance). We convert it into the compact, negated form later, when the data leaves the component.

<Notification emoji="⚠️">
The normal must never be a zero vector. A zero vector cannot be normalized, so the plane would end up as $(0, 0, 0, -D_P)$ and every vertex
of the object would get the same clip distance, $-D_P$. With a positive distance the whole object disappears, and with a zero or negative distance nothing is clipped at all.
</Notification>

to the functionality being described.
</Notification>

## Scene Proxies

In Unreal Engine, gameplay logic is executed on the game thread, while rendering operations—such as updating vertex buffers and managing textures—occur asynchronously on the render thread.
To handle this multi-threaded split safely, the engine creates mirror objects on the render thread for the components living on the game thread.
These objects are known as scene proxies.

Different component types are represented by distinct proxy classes. For instance, a <CodeInline>UPrimitiveComponent</CodeInline> is represented by an
<CodeInline>FPrimitiveSceneProxy</CodeInline>, whereas a <CodeInline>USkyLightComponent</CodeInline> is
represented by an <CodeInline>FSkyLightSceneProxy</CodeInline>. Each proxy stores only the data the renderer needs, and has no direct access to the source component's state or logic.

<Notification>
The same pattern is used between the game thread and the physics thread, with physics proxies instead.
</Notification>

Although data can flow in either direction, information typically moves from the source component to the proxy.
The core challenge of having a mirror object on another thread is keeping the two synchronized as the game state changes.
Before looking at how synchronization works, we have to extend <CodeInline>FPrimitiveSceneProxy</CodeInline> so that it holds the variables to be synchronized in the first place.

<CodeBlock
  code={`
class FPrimitiveSceneProxy
{
    //...
    /** Enables the per-object clip plane on this object. It is not used if r.AllowGlobalClipPlane is not enabled. */
    uint8 bPerObjectClipPlaneEnabled : 1;

    /**
    * Per-object clip plane defined in world space
    * (x, y, z) holds the plane normal in world space (normalized)
    * w holds the distance of the plane from the world origin, negated.
    */
    FVector4 PerObjectClipPlane;
    //...
};
`}
  filename="PrimitiveSceneProxy.h"
/>

The engine relies on an event-driven system for component-proxy synchronization. Since thousands of component-proxy pairs may exist at the same time, polling or updating every proxy each frame would severely degrade frame rates. Instead, the system offers three distinct mechanisms:

1. **Initialization on Creation:** When a rendering-related component registers with the scene, its scene proxy is created. During construction,
   the proxy reads all relevant parameters from the source component, so it begins its lifecycle in a synchronized state.
2. **Recreation (Teardown and Rebuild):** If an existing proxy cannot be modified in place to reflect a change, it is destroyed and recreated from scratch,
   which forces a full synchronization during construction. A prime example is toggling a light's shadow-casting property:
   because of the lighting interactions the proxy has cached with the scene, the change cannot be applied to the existing proxy, so the engine tears it down and rebuilds it.
   This is also how changes made in the Details panel usually reach the renderer, even when an in-place update path exists.
   A component requests a recreation by calling <CodeInline>MarkRenderStateDirty</CodeInline>, which tells the engine that the existing proxy no longer matches
   the rendering state of the source component.
3. **In-Place Dynamic Updates:** An existing scene proxy can be updated to reflect runtime changes made on its source component.
   For example, modifying a component's Custom Primitive Data floats triggers a targeted update that pushes only the modified values to the existing proxy.

All three paths have to be covered for the per-object clip plane to stay in sync, so let us go through them one by one.

### Initialization on Creation

The engine does not create the proxy directly from the component. Instead, it first derives an intermediary description of the component, and then uses that description to create
the scene proxy. The main reason for this indirection is the ability to store a description and create a scene proxy from it later, with or without the source component being present at that time.

To learn more, see the Unreal Fest 2024 talk *How Small Open Doors Can Lead to Better CPU Utilization and Bigger Games* (https://www.youtube.com/watch?v=JaCf2Qmvy18).
</Notification>

</p>


Think of <CodeInline>FPrimitiveSceneProxyDesc</CodeInline> as a photocopy of the component: a lightweight snapshot of everything the proxy needs, taken without holding on to the component itself.
We will extend the description first, so that the clip plane data follows the same route Unreal already uses for bounds, flags and material relevance. Then we will copy
this information into the proxy.

The good news is that the process is simple: we add new variables to the description and store the component's values in them. This is also the right place to convert
the plane into its compact form with the negated distance.

<CodeBlock
  code={`
//Header file
struct FPrimitiveSceneProxyDesc
{
    FPrimitiveSceneProxyDesc()
    {
        //...
        bPerObjectClipPlaneEnabled = false;
        //...
    }

    //...
    uint32 bPerObjectClipPlaneEnabled : 1;
    //...
    FVector4 PerObjectClipPlane = FVector4(0, 0, 0, 0); //Notice the plane is stored in compact form.
    //...
};

//PrimitiveSceneProxy.cpp
//Called by the engine to create a proxy description from a component.
void FPrimitiveSceneProxyDesc::InitializeFromPrimitiveComponent(const UPrimitiveComponent* InComponent)
{
    //...

    //Store all the related information into the description.
    bPerObjectClipPlaneEnabled = InComponent->GetPerObjectClipPlaneEnabled();

    FVector InPerObjectClipPlaneNormal;
    float InPerObjectClipPlaneDistance;

    InComponent->GetPerObjectClipPlane(InPerObjectClipPlaneNormal, InPerObjectClipPlaneDistance);

    // Normalize the normal and negate the distance so the shader can use a single dot product.
    PerObjectClipPlane = FVector4(InPerObjectClipPlaneNormal.GetSafeNormal(), -InPerObjectClipPlaneDistance);
}
`}

/>

The proxy itself is also constructed before the render thread gets involved. Once it is created, it is handed over to the render thread, where <CodeInline>FPrimitiveSceneProxy</CodeInline>
becomes the long-lived "shadow" of the component: still on the CPU, but owned by the renderer. From then on, render thread code reads the clip plane state from the proxy, not from the live component.

The proxy constructor that takes the description, <CodeInline>FPrimitiveSceneProxy::FPrimitiveSceneProxy(const FPrimitiveSceneProxyDesc& InProxyDesc, FName InResourceName)</CodeInline>,
rebuilds the state of the source component from it, so that constructor is our target. All we have to do is copy the values from the description into the mirror variables we defined earlier.

<CodeBlock
  code={`
FPrimitiveSceneProxy::FPrimitiveSceneProxy(const FPrimitiveSceneProxyDesc& InProxyDesc, FName InResourceName)
{
    //...
    bPerObjectClipPlaneEnabled = InProxyDesc.bPerObjectClipPlaneEnabled;
    PerObjectClipPlane = InProxyDesc.PerObjectClipPlane;
}
`}

With that done, the engine carries the per-object clip plane information all the way to the scene proxy when it is created. But this covers only one of the three paths,
so the other two still need our attention.


### Recreation (Teardown and Rebuild)

We cover the teardown path next, since it reuses the creation path we have just implemented. The engine generally takes this path when
the state of the proxy cannot be updated in place. The reasons vary, but they have one thing in common: the engine cannot detect the situation by itself,
so it has to be notified. This is where <CodeInline>MarkRenderStateDirty</CodeInline> comes in handy.

Calling <CodeInline>MarkRenderStateDirty</CodeInline> is enough to force a teardown. Since none of our properties can be applied only at creation time,
the only case where we tear down the scene proxy is when a per-object clip plane property is changed through the Details panel.

The editor calls <CodeInline>UPrimitiveComponent::PostEditChangeProperty(FPropertyChangedEvent&)</CodeInline> whenever a property is changed in the Details panel,
which makes it the natural place to detect changes to our parameters. In fact, the engine already does the same for its own properties:

<CodeBlock
  code={`
#if WITH_EDITOR // Editor only functionality
void UPrimitiveComponent::PostEditChangeProperty(FPropertyChangedEvent& PropertyChangedEvent)
{
    //...
    // we need to reregister the primitive if the min draw distance changed to propagate the change to the rendering thread
    if (PropertyName == GET_MEMBER_NAME_CHECKED(UPrimitiveComponent, MinDrawDistance))
    {
        MarkRenderStateDirty(); // This is how the source code already does it.
    }
    //...
}
#endif
`}
  filename="PrimitiveComponent.cpp"
/>

In the example above, the component reacts to property changes and asks the engine to recreate the proxy when the changed property is <CodeInline>MinDrawDistance</CodeInline>.

We do the same with an if statement that checks whether any of the per-object clip plane properties has changed and, if so, marks the render state as dirty
so that the engine recreates the scene proxy.

<CodeBlock
  code={`
void UPrimitiveComponent::PostEditChangeProperty(FPropertyChangedEvent& PropertyChangedEvent)
{
    //...
    // Recreate the scene proxy whenever one of the per-object clip plane properties changes.
    if (PropertyName == GET_MEMBER_NAME_CHECKED(UPrimitiveComponent, bPerObjectClipPlaneEnabled) ||
        PropertyName == GET_MEMBER_NAME_CHECKED(UPrimitiveComponent, PerObjectClipPlaneNormal) ||
        PropertyName == GET_MEMBER_NAME_CHECKED(UPrimitiveComponent, PerObjectClipPlaneDistance))
    {
        MarkRenderStateDirty();
    }
    //...
}
`}
  filename="PrimitiveComponent.cpp"
/>

<Notification>
In practice, the editor already re-registers a component when one of its properties is edited in the Details panel (see <CodeInline>UActorComponent::PreEditChange</CodeInline>
and <CodeInline>UActorComponent::PostEditChangeProperty</CodeInline>), which recreates its scene proxy as well. The explicit check above follows the engine's own convention,
and keeps the feature working even if that behavior changes in the future.
</Notification>

It is now guaranteed that whenever a primitive component is created, or one of our per-object clip plane parameters is changed at edit time, the engine creates or recreates
the component's scene proxy.

### In-Place Dynamic Updates

Even though recreation always guarantees synchronization, it is generally not the preferred way to keep a proxy in sync with its source component at runtime. Creating
a scene proxy is a non-trivial operation with a performance cost. For example, when a light proxy is created, the engine calculates and caches its interactions with the scene,
which requires a fair amount of random memory access.

To avoid that cost, the general pattern is to provide functions that update scene proxies in place, which external code and the source component can call to keep the two
synchronized. But there is a danger along the way: race conditions.

<Notification>
A race condition occurs when two or more processes or threads access and modify
the same data at the same time, and the final result depends on the order in which
they run. Without proper coordination, this can lead to incorrect or unpredictable results.
</Notification>

Since scene proxies live on the render thread, any change coming from another thread must be handled carefully to prevent race conditions.
A widely used pattern is to define a separate version of the same function for each relevant thread: all versions end up doing the same thing, but each one does it safely for the thread
it is called from. We will follow this pattern and define <CodeInline>SetPerObjectClipPlaneEnabled</CodeInline>
and <CodeInline>SetPerObjectClipPlane</CodeInline> functions, which set <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> and <CodeInline>PerObjectClipPlane</CodeInline>
respectively, for both the game thread and the render thread:

* <CodeInline>SetPerObjectClipPlaneEnabled_GameThread</CodeInline>: Sets the <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> variable, to be called from the game thread.
* <CodeInline>SetPerObjectClipPlaneEnabled_RenderThread</CodeInline>: Sets the <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> variable, to be called from the render thread.
* <CodeInline>SetPerObjectClipPlane_GameThread</CodeInline>: Sets the <CodeInline>PerObjectClipPlane</CodeInline> variable, to be called from the game thread.
* <CodeInline>SetPerObjectClipPlane_RenderThread</CodeInline>: Sets the <CodeInline>PerObjectClipPlane</CodeInline> variable, to be called from the render thread.

Let us define the render thread versions first, since they are simpler.

These functions first check that the call is made on the render thread, and then change the variables. This is safe, because
they are designed to be called on the thread that owns the scene proxy.

The game thread versions, on the other hand, cannot change the variables directly. Instead, they queue a render command that changes the values
on the render thread. The <CodeInline>ENQUEUE_RENDER_COMMAND</CodeInline> macro is designed exactly for this: it lets developers enqueue render commands from threads other than
the render thread, and the render thread executes them in the order they were queued.

Here are the definitions:

## Sending the Data to the GPU

At this point, primitive scene proxies are fully synchronized with the per-object clip plane state of their source components.
However, this information is not useful yet: it resides entirely on the CPU and has not reached the GPU.

Unreal Engine does most of the heavy lifting here, but it still needs a few modifications to carry our data.
Before making them, let us take a look at how Unreal's data pipeline works, since it clarifies the next steps.

Unreal maintains a copy of the scene state on the GPU, called the GPU Scene. The core challenge of this system is keeping the GPU Scene synchronized with the CPU side without introducing performance bottlenecks. Unreal solves this with an incremental update strategy, similar to the one used for scene proxies:

1. When a primitive is added, removed, or modified on the render thread, it is flagged for an update, for example with <CodeInline>RequestGPUSceneUpdate</CodeInline>.
2. For each flagged primitive, the engine derives an intermediate POD (Plain Old Data) structure from its proxy.
3. This structure is serialized into a contiguous stream of <CodeInline>FVector4f</CodeInline> elements right before it is uploaded.
4. The GPU receives this raw memory stream and updates the corresponding part of the GPU Scene buffer.

runtime-updatable property (such as Custom Primitive Data) in your version and follow the same route.
</Notification>

### Marking the Proxies

Unreal generates uniform buffer payloads from the objects in the scene. Different types of objects need different types and amounts of data to be represented correctly on the GPU,
so each type has its own uniform buffer parameter structure. For example, a view produces an <CodeInline>FViewUniformShaderParameters</CodeInline>, while the scene textures, such as the depth and
base color buffers, are described by <CodeInline>FSceneTextureUniformParameters</CodeInline>. Primitive scene proxies are no exception: their structure is called <CodeInline>FPrimitiveUniformShaderParameters</CodeInline>.
Here is its definition:

Like other shader parameter structures, it is a POD type that packs the source object's rendering properties into a compact, GPU-friendly layout.
Because building and uploading this data has a cost, Unreal Engine updates it on demand rather than every frame.

The engine handles initialization and cleanup automatically when a proxy is created or destroyed, but requesting an update when a proxy property changes is the programmer's responsibility.
Whenever a change on the proxy needs to reach the GPU, the proxy has to notify the renderer, which then rebuilds the data from the proxy and uploads it.

Right now, when the per-object clip plane parameters change on a component, the component updates or recreates its scene proxy, but the proxy does not notify the renderer.
In fact, nothing about the per-object clip plane reaches the GPU yet; the next sections take care of that. In this step, we make sure the engine rebuilds the primitive's GPU data
whenever one of the per-object clip plane parameters changes.

The engine provides two functions for this:

* <CodeInline>RequestUniformBufferUpdate</CodeInline>: tells the engine that the primitive's uniform buffer must be rebuilt.
* <CodeInline>RequestGPUSceneUpdate</CodeInline>: tells the engine that the primitive's entry in the GPU Scene must be rebuilt and uploaded.

Both are needed, because primitive data reaches the shaders through two routes: some vertex factories read it from a uniform buffer bound for each primitive,
while most of them read it from the GPU Scene. We will meet these two routes again in the GPU Deserialization section.

With these functions, the render thread setters can notify the scene about their changes:

### POD Data Creation

With these changes, the engine rebuilds the primitive's <CodeInline>FPrimitiveUniformShaderParameters</CodeInline> from the proxy whenever our parameters change, and sends it to the GPU.
However, <CodeInline>FPrimitiveUniformShaderParameters</CodeInline> does not contain any per-object clip plane information yet.

Fixing this requires only small changes to the way Unreal builds <CodeInline>FPrimitiveUniformShaderParameters</CodeInline>. Everything starts with a call to
<CodeInline>FPrimitiveSceneProxy::UpdateUniformBuffer</CodeInline>, which generates a new payload and updates the primitive's uniform buffer.

Let us take a look at it:

<CodeBlock
  code={`

Unreal uses the builder pattern to derive a uniform shader parameter payload from a proxy. A builder is a short-lived object whose only job is to collect values and produce a payload from them.
Different payloads need different builders, and <CodeInline>FPrimitiveUniformShaderParametersBuilder</CodeInline> is the one responsible for producing <CodeInline>FPrimitiveUniformShaderParameters</CodeInline> for primitive scene proxies.

<CodeInline>UpdateUniformBuffer</CodeInline> creates a builder and passes it to <CodeInline>FPrimitiveSceneProxy::BuildUniformShaderParameters</CodeInline>, which fills it with the current state of the proxy.
The builder is then asked to generate a new <CodeInline>FPrimitiveUniformShaderParameters</CodeInline> instance that reflects the values it was given. Finally, this payload is used to update the uniform buffer.

The GPU Scene follows the same route: when a primitive's GPU Scene entry is rebuilt, the engine also calls <CodeInline>BuildUniformShaderParameters</CodeInline> on the proxy and serializes the resulting payload.
So by extending the builder and <CodeInline>BuildUniformShaderParameters</CodeInline>, we cover both the uniform buffer and the GPU Scene.

The builder is the first thing to change if we want to insert our parameters into the payload. <CodeInline>FPrimitiveUniformShaderParametersBuilder</CodeInline> has a lot of functionality,
but only a small part of it is relevant to us. With that in mind, its layout can be simplified as follows:

Boolean variables are handled differently. The goal is to keep <CodeInline>FPrimitiveUniformShaderParameters</CodeInline> as compact as possible, since fewer bytes to upload means faster updates.
Booleans are stored as bytes normally, so each one would waste 7 bits when a single bit is enough. Instead, Unreal reserves a variable named

For every flag, the builder declares a one-bit member and a setter that assigns it. When the payload is built, these values are packed into the <CodeInline>Flags</CodeInline> variable:

It stores each value in the output array by explicitly stating which value goes where. <CodeInline>bPerObjectClipPlaneEnabled</CodeInline> requires no change, since it lives in <CodeInline>Flags</CodeInline>,
which the engine already packs. <CodeInline>PerObjectClipPlane</CodeInline>, however, has to be packed manually.

<Notification>
The memory layout is crucial when it comes to unpacking the data on the GPU side. The GPU receives the data as an <CodeInline>FVector4f</CodeInline> array, with no information about its layout.
Raw memory like this can be interpreted in many ways. For instance, 8 bits of memory can be interpreted either as one unsigned integer or as 8 different boolean flags.

<p align="center">
  <Img src="/blog/implementing-per-object-clip-planes/Image_MemoryInterpretation.svg" alt="Memory Interpretation" />
</p>

Therefore, knowing the exact layout of the data is essential; otherwise, reading it would be like playing the lottery with memory.
This implies a hidden contract between the CPU and the GPU: the packing and unpacking code must agree exactly, one writing and the other reading.

To make sure we do not break this contract, we will update the unpacking code on the GPU side right after the packing code.
</Notification>

We could put the plane anywhere in the array, as long as the GPU side reads it from the same place. We will insert it right before the custom primitive data,
and shift the custom primitive data by one <CodeInline>FVector4f</CodeInline>. Keeping the custom primitive data at the end of the serialized array keeps its index arithmetic simple:
it starts at a fixed index and runs to the end of the primitive's data.

## GPU Deserialization

With the packing and serialization pipeline in place on the CPU side, the final step is for the GPU to correctly unpack the incoming raw memory stream. As we saw earlier,
this relies entirely on the implicit memory layout contract between the CPU and the GPU. If the indices mismatch even slightly, the shaders will misinterpret the raw bytes, leading to severe rendering corruption.

On the GPU side, Unreal Engine handles the deserialization in <CodeInline>SceneData.ush</CodeInline>. To complete our implementation, we need to update the HLSL structure, the data loading functions,
and the flag helpers to mirror our CPU-side changes.

### Unpacking the Data in <CodeInline>GetPrimitiveData</CodeInline>

When a shader needs primitive data, it requests it through <CodeInline>GetPrimitiveData(uint PrimitiveId)</CodeInline>. The function then delegates to the appropriate loader, depending on the platform
and the shader configuration. The branch is chosen at compile time, and there are four possibilities:

1. The shader reads primitive data from a uniform buffer, and instance culling is enabled. The data is read from the bound uniform buffer, rather than from a globally shared one,
   by calling <CodeInline>GetPrimitiveDataFromUniformBuffer</CodeInline>.
2. The shader reads primitive data from uniform buffers, but without instance culling. This is the general case on mobile platforms. It calls <CodeInline>LoadPrimitiveDataUBO</CodeInline>,
   which relies on mobile-specific loading logic to pull the data from the mobile renderer's uniform buffers.
3. The shader is a vertex shader on a platform where vertex shaders cannot access shader resources, which is common for older or restricted mobile hardware. A zeroed instance is returned.
4. If none of the above applies, the primitive data lives in the GPU Scene, a globally shared buffer the shader can access, and it is loaded directly into an <CodeInline>FPrimitiveSceneData</CodeInline> instance.

All four live inside an <CodeInline>#if VF_USE_PRIMITIVE_SCENE_DATA</CodeInline> block. For vertex factories that do not use primitive scene data at all, <CodeInline>SceneData.ush</CodeInline> defines a much simpler
<CodeInline>GetPrimitiveData</CodeInline> that always calls <CodeInline>GetPrimitiveDataFromUniformBuffer</CodeInline>, which is one more reason to keep that function up to date.

#### Reading From the GPU Scene

This path reads from the globally shared GPU Scene buffer. It is a little trickier, since it involves some index arithmetic, but the engine handles most of it. It starts by finding where
the primitive's data begins in the buffer. <CodeInline>PrimitiveId</CodeInline> is the index of the primitive among all the primitives in the shared buffer, and multiplying it by
<CodeInline>PRIMITIVE_SCENE_DATA_STRIDE</CodeInline>, the size of one primitive's data, gives the exact location where that data begins.

<CodeBlock
  code={`

`}

/>

## Clipping Vertices

Everything we have done so far leads to this step, where we finally clip vertices with our per-object clip plane.
Since our implementation extends the engine's global clip plane rather than standing on its own, we will track down the places where the engine's mesh vertex shaders use the global clip plane, and add our code next to it.

Before that, though, it is worth understanding a key concept of how Unreal processes vertices.

### Vertex Factories

Have you ever wondered how the same material can be applied to so many different kinds of meshes, such as static meshes, landscapes, skeletal meshes, or even meshes spawned by Niagara?
Their rendering paths are quite different, and their vertices store different data, yet the same material works on all of them.

The magicians behind this are vertex factories. Unreal uses vertex factories as a geometry-specific abstraction layer between the underlying vertex data and the vertex processing used by the rendering pipeline.
Different geometry types can store vertex attributes in different layouts, and may require different vertex processing operations. A vertex factory describes the vertex input of its geometry type,
and provides the matching shader code to process it.

This allows Unreal's material and shader system to work through a consistent interface, without requiring materials to understand the vertex buffer layout of every geometry type.

Vertex factories have other responsibilities too, but this abstraction is the part that matters to us. As we will see, the shaders we extend do not read the primitive data by themselves:
they call functions that every vertex factory provides.

### Helper Functions

Since we will apply the same clipping logic in multiple places, let us start by defining a few helper functions in <CodeInline>SceneData.ush</CodeInline>. They mirror the engine's own helpers
for the determinant sign flag, such as <CodeInline>GetPrimitive_DeterminantSign_FromFlags</CodeInline>, which live in the same file.

### Extending Existing Shaders

As mentioned earlier, our per-object clip plane is an extension of the engine's global clip plane rather than an independent feature. So we will find the desktop mesh vertex shaders that use the global clip plane
and extend them. The Nanite rasterizer (<CodeInline>NaniteRasterizer.usf</CodeInline>) and the mobile base pass (<CodeInline>MobileBasePassCommon.ush</CodeInline>) use it as well, but they are outside
the scope of this article; see the limitations at the end. The shaders we extend are:

* <CodeInline>AnisotropyPassShader.usf</CodeInline>
* <CodeInline>BasePassVertexShader.usf</CodeInline>
* <CodeInline>DebugViewModeVertexShader.usf</CodeInline>
* <CodeInline>DepthOnlyVertexShader.usf</CodeInline>
* <CodeInline>DistortAccumulateVS.usf</CodeInline>
* <CodeInline>HitProxyVertexShader.usf</CodeInline>
* <CodeInline>LightMapDensityShader.usf</CodeInline>
* <CodeInline>MeshDecals.usf</CodeInline>
* <CodeInline>PositionOnlyDepthVertexShader.usf</CodeInline>
* <CodeInline>VelocityShader.usf</CodeInline>

All of these shaders handle the global clip plane the same way, so we make the same two changes in each of them.

The first is an extra output in the vertex shader's signature. The global clip plane distance is written to <CodeInline>SV_ClipDistance</CodeInline> (which is the same as <CodeInline>SV_ClipDistance0</CodeInline>). We add a second output bound to <CodeInline>SV_ClipDistance1</CodeInline> for our per-object clip plane. The rasterizer interpolates every clip distance across the triangle and discards the parts where any of them is negative, so the two planes work independently of each other.

The second is the distance calculation itself, right after the global clip plane distance. If the per-object clip plane is enabled for the primitive, we evaluate the point-plane distance with the dot product we discussed earlier. Otherwise, we write <CodeInline>0.0</CodeInline>, which never clips anything. Remember that <CodeInline>GetPrimitive_PerObjectClipPlaneEnabledSign_FromFlags</CodeInline> returns -1.0 when the flag is set, which is why we compare the result against <CodeInline>0.0</CodeInline>.

There is one detail to be careful about. The world positions in these shaders are in translated world space, which means they are relative to the camera. This is how Unreal preserves precision in large worlds.
The engine's global clip plane is converted into translated world space on the CPU, so it can be used with these positions directly. Our clip plane, on the other hand, is defined relative to the world origin.
So before evaluating the distance, we move the position back to absolute world space by adding <CodeInline>ResolvedView.WorldCameraOrigin</CodeInline> to its <CodeInline>xyz</CodeInline> part.
<CodeInline>DFHackToFloat</CodeInline> converts the double-float (large world coordinates) representation of the camera origin into a regular <CodeInline>float3</CodeInline>.

Every change is wrapped in <CodeInline>USE_GLOBAL_CLIP_PLANE</CodeInline>, which is why <CodeInline>r.AllowGlobalClipPlane</CodeInline> has to be enabled for our feature to work.

#### <CodeInline>VelocityShader.usf</CodeInline>

The velocity pass writes the screen-space motion of every moving pixel into the velocity buffer. TAA, TSR and motion blur use this buffer to know where each pixel was in the previous frame. If we do not clip here, the clipped part of a moving mesh would still write motion vectors, and motion blur or temporal ghosting would show up where the mesh is not visible. Notice that this shader names its position <CodeInline>TranslatedWorldPosition</CodeInline>, but it is the same camera-relative position we used in the other shaders.

<CodeBlock
  code={`
void MainVertexShader(
  FVertexFactoryInput Input,
  out FVertexOutput Output 
#if USE_GLOBAL_CLIP_PLANE
  , out float OutGlobalClipPlaneDistance : SV_ClipDistance
  , out float OutPerObjectClipPlaneDistance : SV_ClipDistance1
#endif
  //...
  )
{
  //...
  {
    float4 ScreenPos;
    // compute the old screen pos with the old world position and the old camera matrix
    float4 PrevScreenPosObj = mul(float4(PrevTranslatedWorldPosition.xyz, 1), ResolvedView.PrevTranslatedWorldToClip);

    {
      ScreenPos = mul(float4(TranslatedWorldPosition.xyz, 1), ResolvedView.TranslatedWorldToClip);
      Output.Position = ScreenPos;
    }

#if USE_GLOBAL_CLIP_PLANE
    OutGlobalClipPlaneDistance = dot(ResolvedView.GlobalClippingPlane, float4(TranslatedWorldPosition.xyz, 1));
    // Per-object clip plane is enabled
    if (GetPrimitive_PerObjectClipPlaneEnabledSign_FromFlags(GetPrimitiveData(VFIntermediates).Flags) <= 0.0f)
    {
      float3 AbsoluteWorldPos = TranslatedWorldPosition.xyz + DFHackToFloat(ResolvedView.WorldCameraOrigin);
      OutPerObjectClipPlaneDistance = dot(GetPrimitiveData(VFIntermediates).PerObjectClipPlane, float4(AbsoluteWorldPos.xyz, 1));
    }
    else
    {
      OutPerObjectClipPlaneDistance = 0.0f;
    }
#endif

    Output.Interps.PackedVelocityA = INVARIANT(ScreenPos);
    Output.Interps.PackedVelocityC = INVARIANT(PrevScreenPosObj);
  }
  //...
}
`}

### Extending Vertex Factories

Extending the shaders is not enough on its own. Take another look at the code we added to them. To find out whether the per-object clip plane is enabled and to read the plane itself, every shader calls <CodeInline>GetPrimitiveData(VFIntermediates)</CodeInline>, and <CodeInline>PositionOnlyDepthVertexShader.usf</CodeInline> calls <CodeInline>VertexFactoryGetPrimitiveFlags</CodeInline> and <CodeInline>VertexFactoryGetPerObjectClipPlane</CodeInline>. None of these functions is defined in the shaders. They are provided by the vertex factory.

Remember what we said about vertex factories. Every shader we extended includes <CodeInline>/Engine/Generated/VertexFactory.ush</CodeInline>, either directly or, in the case of <CodeInline>BasePassVertexShader.usf</CodeInline>, through <CodeInline>BasePassVertexCommon.ush</CodeInline>. This file does not exist on disk. When the engine compiles a shader for a specific vertex factory, it generates this file so that it includes the shader file of that vertex factory. As a result, the same <CodeInline>BasePassVertexShader.usf</CodeInline> gets compiled once with <CodeInline>LocalVertexFactory.ush</CodeInline>, once with <CodeInline>HairStrandsVertexFactory.ush</CodeInline> and so on, once for every vertex factory a material can be used with.

HLSL has no virtual functions or interfaces. The only thing that holds this system together is a convention: every vertex factory has to define every function the shaders call, with the same name and signature. If a single vertex factory is missing one of them, every shader permutation compiled with that vertex factory fails to compile. So by calling new functions in the shaders, we also have to make sure every vertex factory that reaches those shaders defines them.

Most vertex factories, such as <CodeInline>LocalVertexFactory.ush</CodeInline> and <CodeInline>LandscapeVertexFactory.ush</CodeInline>, already define <CodeInline>GetPrimitiveData(FVertexFactoryIntermediates)</CodeInline> because the engine itself uses it in other places. But a few of them do not, and the position-only helpers are completely new. This leaves us with two groups of changes:

* <CodeInline>LidarPointCloudVertexFactory.ush</CodeInline> and <CodeInline>HairStrandsVertexFactory.ush</CodeInline> need <CodeInline>GetPrimitiveData</CodeInline>.
* <CodeInline>GeometryCacheVertexFactory.ush</CodeInline>, <CodeInline>GeometryCollectionVertexFactory.ush</CodeInline>, <CodeInline>LocalVertexFactory.ush</CodeInline> and <CodeInline>LidarPointCloudVertexFactory.ush</CodeInline> support the position-only depth pass, so they need <CodeInline>VertexFactoryGetPrimitiveFlags</CodeInline> and <CodeInline>VertexFactoryGetPerObjectClipPlane</CodeInline>.

<Notification>
A vertex factory supports the position-only depth pass when its C++ side declares the <CodeInline>EVertexFactoryFlags::SupportsPositionOnly</CodeInline> flag.
Some vertex factories, such as the one in the Water plugin, define a position-only <CodeInline>VertexFactoryGetWorldPosition</CodeInline> without declaring the flag. The position-only shader is never compiled for them,
so they need no changes.
</Notification>

## Conclusion

That is all it takes. Once the engine is compiled with these changes and the global clip plane feature is enabled, the per-object clip plane is ready to use. The feature can be enabled in **Project Settings → Engine → Rendering** with the **Support global clip plane for Planar Reflections** option, or by setting <CodeInline>r.AllowGlobalClipPlane=1</CodeInline> in the <CodeInline>[/Script/Engine.RendererSettings]</CodeInline> section of <CodeInline>DefaultEngine.ini</CodeInline>. Since this option changes the shaders themselves, the editor has to be restarted, and the first launch triggers a shader recompile. After that, every primitive component shows the per-object clip plane properties in the Rendering category of its Details panel, and gameplay code or Blueprints can drive the plane at runtime with <CodeInline>SetPerObjectClipPlaneEnabled</CodeInline> and <CodeInline>SetPerObjectClipPlane</CodeInline>.

### Limitations and Possible Improvements

This implementation covers the most common rendering paths, but it is far from complete. Since we only extended the shaders that already support the global clip plane, everything the global clip plane does not touch is not affected by our plane either. Here are the most important gaps, and a few improvements that would make the feature more useful.

* **Nanite:** Nanite meshes do not go through the vertex shaders we extended. They are rasterized by Nanite's own rasterizer, partly in hardware and partly in a software rasterizer running in compute shaders. The software path cannot rely on <CodeInline>SV_ClipDistance</CodeInline> at all, so the distance test has to be done manually per triangle or per pixel. On top of that, the cluster culling would need to know about the plane, so clusters that are fully clipped are not drawn at all. Until then, a mesh needs Nanite disabled to be clipped.
* **Shadows:** The shadow depth passes are not among the shaders we extended, so the clipped part of a mesh still casts shadows. Extending the shadow depth vertex shaders would fix this for regular shadow maps. Virtual shadow maps render Nanite geometry through the Nanite rasterizer, so for Nanite meshes they depend on Nanite support as well.
* **Ray tracing and Lumen:** Ray tracing does not rasterize triangles, so clip distances have no meaning there. Hardware ray-traced reflections, shadows, path tracing and Lumen still see the whole mesh. Supporting them would require an any-hit shader that rejects the hits behind the plane, which is expensive. Lumen's software tracing uses mesh distance fields and its surface cache, which are both built from the full mesh, so the clipped part can still show up in indirect lighting and reflections.
* **Distance field effects:** For the same reason, distance field shadows and distance field ambient occlusion still use the unclipped shape of the mesh.
* **Mobile:** The mobile renderer has its own base pass shaders (such as <CodeInline>MobileBasePassVertexShader.usf</CodeInline>), which we did not extend, and we also skipped the mobile path of <CodeInline>GetPrimitiveData</CodeInline>.
* **Capping the cut:** Clipping only removes geometry; it does not close the hole. When a closed mesh is cut, you look inside it and see its back faces, or nothing at all if they are culled. A proper cross-section effect needs the cut surface to be capped, which is usually done with a stencil technique or by shading the back faces with a flat color.
* **Collision and queries:** The clip plane is purely visual. Physics, line traces and overlaps still use the whole mesh, so a gameplay system that relies on the clipped shape has to account for it separately.
* **Precision:** We reconstruct the absolute world position in single precision and evaluate the plane in world space. Far from the world origin, this loses precision and the cut can start to wobble. Converting the plane into the camera-relative (translated world) space on the CPU, where double precision is available, would avoid this completely.
* **Local-space planes:** The plane is defined in world space, so it does not follow the object when it moves or rotates. An option to define the plane relative to the primitive would be useful for effects that should stick to the object.
* **Multiple planes:** The hardware provides up to eight clip distances, and we use only two of them. The same approach could be extended to support several planes per object, for example to cut out a box-shaped region.
* **Cost:** Enabling <CodeInline>r.AllowGlobalClipPlane</CodeInline> adds an extra clip distance and a branch to the vertex shaders of every mesh in the project, even the ones that never use a clip plane. The setting's own tooltip warns that it increases the base pass triangle cost by around 15%, whether planar reflections are active or not. A dedicated shader permutation, enabled only for the primitives that need it, would remove this cost from the rest of the scene.

Even with these limitations, the implementation shows how much can be achieved by extending what the engine already has. A single new property travels all the way from the editor, through the scene proxy and the GPU Scene, into the vertex shaders, and finally reaches the rasterizer. I hope it helps you understand how data flows from the game thread to the GPU in Unreal, and gives you a good starting point for your own rendering features.
