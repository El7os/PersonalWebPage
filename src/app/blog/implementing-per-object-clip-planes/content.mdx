## - Introduction
In modern real-time rendering, specialized visual effects, gameplay mechanics, and visualization tools often require geometry to be dynamically clipped.
While Unreal Engine 5 provides robust support for global clip planes—typically utilized for planar water reflections—it 
lacks out-of-the-box support for isolating this behavior on a per-object basis.


When global clip planes are enabled, Unreal Engine uses one of the hardware's clip-distance slots to discard vertices before rasterization.
The plane's position and orientation are defined per camera, which is ideal for reflections; however, this applies uniformly 
to every object that the camera draws. While different cameras can carry different global planes, every primitive within a single 
view shares the same cutting boundary. This global scope is the exact bottleneck our implementation addresses.


Multiple clip distances can be active simultaneously, and modern graphics APIs typically expose six to eight slots.
Our implementation occupies a different slot than the engine's global clip plane so that both can coexist: water reflections 
retain their camera-driven plane, while individual objects can carry their own.

Implementing per-object clip planes allows developers to slice, hollow out, or selectively cull geometry on specific primitives without 
affecting adjacent elements in the scene. This capability is crucial for applications ranging from architectural visualizations and medical 
imaging to sci-fi cross-section effects.


The goal is to extend Unreal Engine's existing global clip-plane architecture by defining the plane used to derive clip distances 
on a per-object basis, enabling each primitive to expose its own independent cutting boundary. This utilizes the same underlying 
hardware feature and identical dot-product mathematics, but introduces a separate control lane that artists and gameplay systems 
can drive independently.


To understand how to inject this custom logic into the rendering pipeline, we must first look at how the hardware handles 
clipping boundaries under the hood.

## - What Are Clip Planes And Where to Find Them

In computer graphics, the hardware relies on a dedicated set of distances to determine whether a vertex should be clipped.
Rather than executing software-side culling algorithms, modern graphics APIs (such as DirectX, Vulkan, and OpenGL) natively 
utilize specialized hardware registers allocated for these clip distances—typically supporting a minimum of six to eight simultaneously.


During the vertex processing stage of the rendering pipeline, the hardware evaluates these calculated distance values.
If a vertex yields a negative clip distance, the hardware rasterizer clips the primitive along this boundary, cleanly discarding non-visible
fragments before they ever reach the pixel shader. Essentially, the hardware monitors each active clip distance slot and discards the vertex
if even a single distance value falls below zero.


Generally, developers use a plane equation to derive this clip distance value. An arbitrary plane is defined, and the clip distance
is calculated as the signed distance from the vertex to that plane. If the vertex lies in the positive half-space—the side the plane
normal points toward—the distance value is positive and the geometry is preserved. Conversely, if it lies on the opposite side, the distance
value becomes negative, triggering the hardware to clip the vertex.

<MathBlock

  caption="Setting the clip distnace to the distance of point Q to a plane"
  size="large"
/>


Because using a plane equation to derive these values is the industry-standard approach, this hardware feature is universally referred to as "clip planes."


Out of the box, Unreal Engine supports a global clip plane feature. When enabled, the engine evaluates every vertex against a single 
plane defined on a per-camera basis to derive its clip distance. The term "global" reflects the fact that this
boundary applies uniformly to every object rendered by that specific camera—though different cameras can maintain entirely distinct
global clip planes.


The goal of our implementation is to extend this capability to a per-object basis. We will leverage the exact same
underlying hardware mechanics, but define the clip plane dynamically per primitive so that individual objects can maintain
their own unique cutting boundaries. Since modern graphics APIs support multiple concurrent clip distances, we can assign our
custom per-object plane to a completely separate hardware slot. This ensures our implementation can seamlessly coexist with the
engine's native global clip plane. Before diving into the implementation it is important to understand how the clip planes are 
represented and the signed distance is calculated.


### - The Math: Compact Plane Representation

Mathematically, an infinite plane is defined by the following equation:

<MathBlock
  latex="\vec{N} \cdot (\vec{P} - \vec{P}_0) = 0"
  caption="Plane Equation"
  size="large"
/>

Where $\vec{N}$ is the surface normal vector of the plane and $\vec{P}_0$ is an arbitrary point lying on that plane.

From this equation, it can be deduced that two <CodeInline>FVector3f</CodeInline>s are required to represent a 3D plane in world space. 
However, it is possible to express a plane in a much more compact form. A 3D plane can be fully defined by a single <CodeInline>FVector4f</CodeInline> if 
if we define $\vec{P}_0$ relative to the world origin using the signed distance $D_p$ as follows:

<MathBlock
  latex="\vec{P}_0 = D_p * \vec{N}"
  caption=""
  size="large"
/>

Geometrically, this approach defines $\vec{P}_0$ aGeometrically, this approach defines $\vec{N}$ intersects the plane surface.

<p align="center">

Under this condition, the plane is elegantly represented by storing the components 
of the normal vector $\vec{N}$ in the first three elements $(X, Y, Z)$ of the <CodeInline>FVector4f</CodeInline>,
and the scalar distance $D_p$ in the final $W$ component.

This compact representation reduces the memory footprint of a plane by two floating-point
values. Furthermore, expressing a plane in this 4D vector format unlocks highly efficient
methods for performing plane-point distance tests, which we will explore next.

### - Evaluating Point-Plane Distance (The Magic Dot Product)


When clipping vertices along a plane, calculating the signed distance from a point to that
plane is an unavoidable necessity. While there are multiple ways to interpret this mathematically,
one specific geometric interpretation proves incredibly elegant for our implementation.

To ground this concept in our rendering pipeline, we can establish a clean mathematical
framework by defining a few key variables and our ultimate objective:

* $\vec{Q}$: The point of interest (the vertex position in world space).
* $D_Q$: The signed distance of the query point $\vec{Q}$ from the clipping plane,
  which we will refer to as the clip distance moving forward. Our primary goal is to solve for this value.
* $D_P$: The scalar distance satisfying the equation $\vec{P}_0 = D_P \cdot \vec{N}$. In other words, it represents the signed perpendicular distance of the plane from the world origin along the normal vector.


The shortest distance from an arbitrary point to a plane is always measured along a path perpendicular to that plane. Because the plane normal $\vec{N}$ is by definition perpendicular
to the surface, $D_Q$ can be computed by projecting the query point $\vec{Q}$ onto the plane
normal. The difference between this projected distance and the plane's own distance from 
the origin ($D_P$) yields the exact signed distance $D_Q$.


The geometric interpretation is illustrated below:


<p align="center">
  <img src="/blog/implementing-per-object-clip-planes/Image_Plane_Distance.svg" alt="Plane"></img>
</p>

Therefore, the relationship can be expressed as:

<MathBlock
  latex="D_Q = \vec{Q} \cdot \vec{N} - D_P"
  caption=""
  size="large"
/>

By expanding and slightly rearranging this equation, a magnificent algebraic shorthand reveals itself:

<MathBlock
  latex="\begin{align*}
         D_Q &= \vec{Q} \cdot \vec{N} - D_P \\
         D_Q &= Q_X * N_X + Q_Y * N_Y + Q_Z * N_Z - D_P * 1 \\
         D_Q &= <N_X, N_Y, N_Z, -D_P> \cdot <Q_X, Q_Y, Q_Z, 1> 
         \end{align*}"
  caption=""
  size="large"
/>


Notice that the left-hand operand is almost identical to our previously discussed 4D 
vector representation of the plane, with the minor exception that the distance 
term $D_P$ is negated. The right-hand operand is simply the query point represented 
as a homogeneous 4D coordinate, obtained by appending $1$ as its $W$ component. 
Evaluating the dot product of these two 4D vectors directly yields the signed clip 
distance of $\vec{Q}$.

This means that if the $D_p$ term is negated while representing the clip plane, then calculating 
the distance of point $\vec{Q}$ from the clip plane is as trivial as evaluating the dot product of the plane and the point 
represented as a homogeneous 4D coordinate.


## - Implementation

Bridging the gap between gameplay code and raw hardware clipping requires establishing a unified, 
sequential data pipeline that stretches all the way from <CodeInline>UPrimitiveComponent</CodeInline> down to actual shaders.
We will follow a top-down approach—tracing the data's journey sequentially through
the engine's architectural layers. Along this path, our primary task is to safely ferry our parameters across the asynchronous 
Game Thread/Render Thread barrier without risking race conditions, and pack them neatly across the CPU-to-GPU memory interface.

## Step 1: The Game Thread (Defining the Source Data)


### Extending <CodeInline>UPrimitiveComponent</CodeInline>

The first step is to extend the <CodeInline>UPrimitiveComponent</CodeInline> class to add support for per-object clip planes. 
<CodeInline>UPrimitiveComponent</CodeInline> is the base class for any component that possesses a visual 
representation or physical volume in the game world. Integrating the data required 
for our per-object clip plane at this level ensures that the feature automatically 
works with static meshes, skeletal meshes, and any other custom primitives that inherit
from this base class.


To support this feature, we only need to store three pieces of information:

* A boolean flag indicating whether the component has an active per-object clip plane.

* A <CodeInline>FVector3f</CodeInline> representing the surface normal vector of the clip plane in world space.

* A floating-point value representing the signed perpendicular distance of the clip plane from the world origin.


Because this structural data will eventually be exposed to technical artists and designers
in the editor, it is worth keeping the interface intuitive, self-explanatory, and 
well-documented within the details panel.

## Step 3: The GPU Scene Pipeline (Inducing the Builder)

With that being the all the implementation required to carry the information from the game thread to the proxies at the render thread is done.

The next step is to carry the information to the GPU before using those values in shaders to cull actual vertices.

But, to accomplish this stage a meta undestanding of unreal's buffer information pipeline should be undestood.
Even though proxies are the shadows of the game objects on the render thread they are still reside in the CPU. GPU has no idea about those 
objects. Unreal solves this issue by generating something called primitive uniform shader parameter. Unreal employs a collection of shader 
parameters and call them <CodeInline>FPrimitiveUniformShaderParameters</CodeInline>. The parameter collection is basically a sequence of 
float4 data which are treated as raw memory units. The information about the primitive is serialized into those parameters and send to the GPU based on
an agreed packing configuration, such as 34th Fvector4f  represents the object location in camera space etc.

<br></br>

The general pipeline is very similar with the previous one. Inspect the following diagram.

Since creating a FPrimitiveUniformBufferParameters of an object, which is going to be referred as uniform buffer of an object, is not an efficent
thing to do every frame the engine follows an event based system. It creates the uniform buffer when a primitive proxy is craeted or when a uniform buffer
is marked as dirty , indicating a recent change in the proxy's state which concerns the GPU as well. 

<br></br>

The first one is handled by the engine but the second requires a little bit extra. Since per object clip plane parameters are newly introduced the engine
does not know that it should regenerate the uniform buffers of the object when those variables are changed. 

### Thread-Safe Communication via ENQUEUE_RENDER_COMMAND

Therefore we need to tell the engine that when per-object clip plane parameters are changed it should regenerate the buffers.
Luckly we are halfway there. Do you remember the functions that we call to notify the scene proxy about the changes made in the component,
well it is time to revisit and define them.

<br></br>

Those functions were <CodeInline>SetPerObjectClipPlaneEnabled_GameThread(bool)</CodeInline> and <CodeInline>SetPerObjectClipPlane_GameThread(FVector4)</CodeInline>

Notice, functions has _GameThread_ suffix. This is because these functions are designed to be called only in game thread. Their definitions
are going to call their _RenderThread_ versions and then those functions are going to mutate the variables of the proxy. But additionally since 
per-object clip plane releated variables are also changed with that call it is a good place to let the engine know that it should update the
uniform buffers.

## Step 4: The Finishing Touch—Shader Modifications (HLSL Stage)

At this point the clip plane lives in GPU memory, patiently waiting to do its job. The CPU side of the house is in order; what remains is teaching the vertex shader to read that packed data and write a clip distance the rasterizer understands. This is where our earlier dot-product math pays off—we already know exactly what value to emit.

### Intercepting Primitive Data in SceneData.ush

Unreal centralizes per-primitive fetches in <CodeInline>SceneData.ush</CodeInline>. Any shader that calls <CodeInline>GetPrimitiveData</CodeInline> expects a stable layout: the flag bit we claimed in <CodeInline>SceneDefinitions.h</CodeInline> and the float4 at stride index 34 must be mirrored here so HLSL sees the same contract the C++ <CodeInline>Setup()</CodeInline> function wrote. We extend the struct and accessor helpers so materials and vertex factories can query <CodeInline>PerObjectClipPlane</CodeInline> without bespoke uniform slots.

### Injecting the Clip Distance into the Vertex Shader (PositionShader.usf)

Finally, the vertex shader must output the hardware clip distance when the per-object flag is set—typically a second clip distance index so the engine's global plane keeps its slot. In <CodeInline>PositionShader.usf</CodeInline> (and the relevant vertex factory paths), we evaluate the same dot product derived in the math section, guard it behind the flag bitmask, and assign the result to the appropriate <CodeInline>OutClipDistance</CodeInline> semantic. Flip the normal if your art direction wants the opposite half-space clipped; the math does not care, but your level designers might.
